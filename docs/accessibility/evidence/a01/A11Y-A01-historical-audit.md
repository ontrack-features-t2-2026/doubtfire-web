## How elements were deduplicated

1. Resolve each JSON `filePath` to its repository-relative path and verify the embedded source against the immutable Git blob.
2. Use the diagnostic start location to locate the actual opening `<tag` in that source. Scan through quoted attributes to the end of that opening tag; record its tag name and directly bound event names.
3. Identify a source element by **revision + file path + byte offset of its opening tag**. The `E001`–`E025` labels are stable aliases assigned in captured message order. Diagnostic end lines/columns are retained as evidence but are **not** used as the element identity.
4. Count the set of these identities within each rule/file and the union across rules. Do not combine nested elements solely because one diagnostic range contains another.

Two examples prevent misleading deduplication:

- `unit-task-editor.component.html:186` and `:217` are **two different elements**. The row directly binds `(click)="selectTaskDefinition(taskDefinition)"`; its inner action-group div directly binds `(click)="$event.stopPropagation()"`. Their ranges overlap, but both opening tags carry their own handlers. Together they produce four messages and count as two elements.
- `attachment-confirmation-dialog.component.html:1` spans 62 lines but directly binds `(keydown.enter)` on the outer div. It is one genuine focus-rule element, not an ancestor duplicate to discard. The appropriate design question is whether to remove or narrow the Enter interception, not whether to make an inert dialog wrapper another tab stop.

### Ancestor-bubbling caveat and lint blind spots

The mouse rule in template-plugin 22.0.0 uses descendant-aware selectors equivalent to `Element:has(BoundEvent[mouseover]):not(:has(BoundEvent[focus]))` and the matching mouseout/blur pair. The same descendant mouse handler can therefore make multiple ancestor elements match. This is **selector ancestry**, not proof of several independent mouse handlers or several defects. Conversely, a descendant's focus/blur handlers can satisfy an ancestor even when the ancestor itself has no keyboard equivalent. The rule does not establish that a focus handler is reachable or that the keyboard behavior is correct.

The August ticket describes eight mouse messages around one tutor-discussion element and ten around one comments-viewer element. Those historical examples explain why raw message totals must not be treated as defect totals; the August JSON and exact audited revision were not supplied here, so their full deduplicated total is not independently reconstructed. In the retained September snapshot there are **no mouse messages to collapse**. Its reduction from 37 messages to 25 distinct elements comes entirely from the 12 click/focus pairs.

All 25 observed elements were inspected at their opening tags, including their direct handlers. Native semantics, accessible names, disabled/hidden states, actual keyboard activation, nested controls, focus visibility, and runtime permissions still need behavioral validation; passing four lint rules is a limited static check, not WCAG certification or a full defect count.

After that, the marginal focus-rule work is principally its two focus-only elements plus verification. One rule per enforcement PR makes regressions, residual counts, and review dependencies easier to inspect without splitting a single control into an unusable intermediate design.
