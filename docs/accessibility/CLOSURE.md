## Run once, attach the evidence to each relevant ticket

1. Attach the completed A01 report and table to its card; the technical work is already supplied above.
2. Verify a synthetic runtime and fill the run record's environment and fixture tables. Use a fresh record for every different web/API/deploy commit combination.
3. Complete the student and staff procedures: ST1–ST6 and SF1–SF6. Record K/S/V checks separately; do not turn a rendered unit test into a browser or screen-reader pass.
4. Have an independent validator review the current implementation and record V01. Have two independent people complete the four U1 tasks without coaching.
5. Add observed findings to the remediation register, fix and re-test them as needed, then obtain the named reviews and decisions below.
6. Link the documents, PRs, exact commits, run records, finding/re-test evidence and actual approvals to the appropriate cards. Update checklist/status fields only when their evidence exists. Keep PR review and merge decisions with the authorised reviewers; this guide does not require self-merging.

One observed result may support A03/A04, F05/F06/F07, V01 and MVP01 when the **same actual web/API/deploy commits, fixture, route, role, browser/OS/assistive technology, viewport, theme and preference state** were used. Link the same run row from each ticket; do not copy it as a new run. Record any justified equivalence explicitly. A changed commit or environment requires a new record and a scoped re-test; earlier evidence remains historical. Automated DOM checks, isolated CSS geometry tests and colour calculations can be cited alongside human checks, but do not replace them. A reused author-run result does not meet an independent-review requirement.

## Baseline platform coverage and practical setup references

Use [baseline Section 5](https://github.com/ontrack-features-t2-2026/doubtfire-web/blob/94068e0758954791e074f723602cd44792a3684b/docs/A11Y-D01-Accessibility-Baseline_Phase1.md#5-test-environment-matrix) when the lead confirms the approved acceptance scope. Its matrix includes Windows/NVDA with Chrome or Firefox, macOS/VoiceOver with Safari, real iOS/VoiceOver with Safari and real Android/TalkBack with Chrome, plus the listed browser alternatives. JAWS is additional where available. Record unsupported or unavailable combinations as **Not run / coverage gap**, with an owner and follow-up; obtain the lead's scope decision rather than inventing a pass or a new certification gate.

For each available mobile platform, repeat the student and staff journeys in the **normal browser and installed standalone PWA**. Verify that the installed app serves the same recorded build; service-worker caches may differ. Use touch exploration and swipe navigation, portrait and landscape, and the on-screen keyboard closed/open. Include launch/resume, returning from the file picker or document viewer, device/browser back navigation, safe-area insets, focus after pane changes, touch targets and large text. The selected task and required submission/feedback controls must survive those transitions. The 390×844 CSS-pixel browser fixture and desktop responsive emulation complement real-device tests; they do not establish an iOS, Android or PWA pass.

For Mac setup, Command-F5 toggles VoiceOver (function-key settings may also require Fn). Confirm the configured VO modifier, commonly Control-Option, and record the actual setting; use the built-in tutorial/help if unfamiliar. See [Apple's VoiceOver commands](https://support.apple.com/en-ie/guide/voiceover/cpvokys01/mac).

Use the measured conditions in the W3C explanations for [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html), [text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) and [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html). Record any applicable exception for a specific element, rather than exempting an entire route.

Chrome's Rendering panel can emulate `forced-colors: active` and `prefers-reduced-motion: reduce`; [Chrome's instructions](https://developer.chrome.com/docs/devtools/rendering/emulate-css) describe the controls. Label these results **CSS media emulation**. Keep separate rows for a real OS high-contrast/forced-colour mode and OS reduced-motion setting; emulation does not establish assistive-technology or device acceptance.
